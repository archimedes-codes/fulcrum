# T1 — CI process census: fail the run when a daemon or worker outlives the test suite (issue #5)

**Goal:** A shell guard, `scripts/check-no-stray-processes.sh`, wired into `.github/workflows/ci.yml` on all three OS legs AFTER `cargo test`, that fails the job when a `fulcrum` daemon or worker process from THIS run is left alive — while never false-positiving on an unrelated `fulcrum` a developer left running on a self-hosted runner.

**Architecture:** The guard enumerates the process table by image name on each platform, feeds the enumeration through ONE pure classify function (the same function the `--self-test` fixtures exercise), and distinguishes "from THIS run" from "somebody else's" with an env-var run-scoping discriminator: the CI step exports a unique per-run value before `cargo test`, and every process the suite spawns inherits it. Truncation is handled UP FRONT, not discovered in CI: because `comm` is hopelessly truncated to 15 chars, the unix census enumerates with `ps` (the full command line), never `pgrep -x`, and a candidate is classified as THIS run's only when `ps`'s argv **and** its `/proc/<pid>/environ` both carry this run's exact secret. State lives in the CI shell step and the caller environment, NEVER in the Rust tests (the repo's measured `worker_mode.rs` shared-sweep disaster is the recorded reason no shared runtime state is added).

**Tech Stack:** bash (the `bash` that `actions/checkout` guarantees on all three legs, same as the existing `check-rquickjs-allocator.sh`), `ps` + `/proc/<pid>` on Linux, `ps eww … args` on macOS, `tasklist` on Windows, GitHub Actions `env:` / `GITHUB_ENV`.

### Task 1: the stray-process census script + the CI step pair

**Parallel:** none — single task.

**Context:**

During T9 development, 34 stray `fulcrum serve` daemons accumulated on a developer machine: the suite spawned daemons and lost track of them (worker_mode.rs:49-53 records them, some 5.5 hours old). The per-test fix — every test kills and reaps its own children (`Spawned::drop` kills+waits unconditionally, worker_mode.rs:743-759; each daemon test asserts `pid_is_reaped(daemon_pid)` after dropping the handle) — is per-pid and LOCAL: each guard asks "is the specific pid I spawned gone?"; nobody asks "are there leftover daemon/worker processes from THIS run that nobody is tracking?". A test that crashes before recording a pid, or spawns a grandchild it never tracked, passes every existing assertion and still leaks. This task's census is the whole-table form of that per-run question, as a CI step that must run AFTER `cargo test` (that is when leaks materialise).

`fulcrum serve` never exits on its own (`serve::run` never returns), so ANY `fulcrum` left running after the tests is by construction a leak. The image names the census must consider are `fulcrum`, `fake_worker_core`, `fake_mcp_stdio_core` — `_core` is load-bearing (workspace members share one `target/debug/`; cargo only WARNS on bin-name collisions — never "simplify" it).

The hard requirement from issue #5: the census must distinguish a process FROM THIS RUN from a developer's unrelated `fulcrum` on a self-hosted runner. Hosted runners are clean checkouts; self-hosted ones are not. **Nothing in this repo reads `GITHUB_*`/`RUNNER_*` today — this task defines that precedent** (grounding report §5: zero `GITHUB_`/`RUNNER_`/`self-hosted` references anywhere in the tree).

**The run-scoping discriminator this plan chooses (documented here and reproduced as a header comment in the script — these are T1's semantics, defined by this task because nothing in the tree defines them):**

> The CI job exports `FULCRUM_CI_RUN_MARKER` — a fresh unguessable value derived from `github.run_id` + `github.run_attempt` — into the environment shared by every step of the leg, BEFORE `cargo test` runs (workflow `env:`). The marker is inherited by every process the suite spawns (see the propagation verification below, which was checked against the tree and is written up in the plan, not left to be discovered in CI).
>
> **Unix (Linux + macOS):** the census enumerates by image name using `ps` (full command lines), and for each candidate whose argv carries `<image-path> …` reads the candidate's OWN `/proc/<pid>/environ` (Linux) — the discriminator is: *a process belongs to THIS run iff that environ contains a line `FULCRUM_CI_RUN_MARKER=<this run's exact value>`*. Scoped-in processes are killed and count as leaks; scoped-out ones are reported and left alone (count reported to stderr, exit stays 0). The value-match (not mere presence) is what makes a locally-exported marker useless to a developer's `fulcrum`. The environ read is the load-bearing proof the process is a daemon/worker of THIS run; on macOS the read is unverifiable from this machine (see "macOS run-scoping is UNVERIFIED", below).
>
> **Windows:** no bash-accessible mechanism can read another process's environment (no procfs; reading the PEB's `ProcessParameters->Environment` needs a compiled helper with process handles, which is outside this task's owned file set). Issue #5 asks to fail the run on all three legs. A `Get-CimInstance Win32_Process`-style parent-PID-tree discriminator cannot deliver attribution for THIS run on a self-hosted runner (a candidate's `ParentProcessId` chain usually bottoms out in the `cargo test` process, whose own `ParentProcessId` is the runner agent that ALSO hosts a developer's concurrently-running `fulcrum` — attributing by ancestry is a false-positive machine for the exact violation that issue #5 names). **Decision: the Windows leg is ADVISORY — explicitly, in the plan, in the script's header comment, in the script's own output, and in the status-file follow-ups: on Windows every live `tasklist` image match is reported as a leak (never killed), with a banner that this leg is advisory because process-to-RUN attribution is impossible without a compiled env-reading helper; enforcement of the issue's criterion is met on unix only.** The reason for the decision is recorded here and in the script: hosted `windows-latest` runners are a clean image by GitHub's contract, so on every runner this repo actually uses the advisory leg is still effective — and issue #5's "fail the run" criterion is enforced where attribution is provable and honestly labelled advisory where it is not.
>
> **Outside CI (no marker exported):** the census refuses with exit 2 and a human instruction. No marker recorded is NOT "clean" — the census answers only "are there processes from THIS run left", and without the discriminator it cannot read the question.

**Why `ps`, and why `pgrep -x` is NOT used (measured, not hypothesised):**

`pgrep -x` matches against `comm`, and the kernel truncates `comm` to **15 characters**. Measured on this machine (procps-ng 4.0.6, kernel `TASK_COMM_LEN`):

- a process running as `/tmp/…/fake_worker_core` has `comm = "fake_worker_cor"` (15 chars);
- a process running as `/tmp/…/fake_worker_corruptor` (24 chars) ALSO has `comm = "fake_worker_cor"` — truncation is a **prefix collision, not a safe truncation**: `pgrep -x fake_worker_cor` returns BOTH pids, so "matching the truncated form" without a second discriminator would kill an unrelated `…_corruptor`;
- `pgrep -x fake_mcp_stdio_core` (19 chars) prints `pgrep: pattern that searches for process name longer than 15 characters will result in zero matches` and exits 1 no matter what is running (its 15-char comm is `fake_mcp_stdio_`); confirmed by the two live probes above: full-name `pgrep -x` exits 1 with the warning while `pgrep -x fake_mcp_stdio_` matches;
- `fulcrum` (7 chars) is fine under `pgrep -x`, but a census that needs `ps` for the two fixtures anyway should use ONE enumerator for all three images — a mixed `pgrep`-for-the-short-one / `ps`-for-the-long-ones path is two mechanisms doing one job, and the second mechanism (ps) is the one that must be exercised in CI for the fixtures to be covered at all.

A `ps`-based enumeration was chosen over `pgrep -x` on truncated names:

- `pgrep` has no whole-argv option that is exact — `pgrep -f <string>` matches ANY command line containing the string (a 60k-line test binary path under `target/debug/deps/` contains `fake_worker_cor` on a real developer machine) and `pgrep -f '<full name>$'` still cannot tell `…/fake_worker_corruptor` from `…/fake_worker_core` because the name is not the last argv element (the fixture bins take no trailing args that terminate the string, and the daemon's argv ends in `--worker-exe <path>`).
- `ps` can be exact AND scoped: enumerate with `-o pid=,comm=,args=` and filter on the FULL basename (`fake_worker_corruptor` is rejected, `fake_worker_core` is not — measured above: the `args=` column prints the untruncated argv, which comm's 15-char truncation destroyed). This restores the exactness that `pgrep -x` lost to truncation.
- The garbage-in guard is not `pgrep`'s warning; it is the census's own vacuity floor: the enumerate step must parse a `args=` column, and a parse failure is a refusal (exit 2), never "clean".
- Zombies: `ps` DOES list a zombie candidate under its parent (measured: `ps -o stat= -p <z>` shows `Z`); a zombie is a real leak-symptom worth reporting, so the census keeps it and counts on the re-probe (kill/`ps` re-list) to catch it — see `kill_leak` below.

**The one exemption — the census's own process:** the census's own argv contains `check-no-stray-processes` and never an image name, so server-side image filtering needs no self-filter. `ps`/`tasklist` are filtered per-image; the census itself is invisible to every filter (it is not running as `fulcrum` / `fake_*`).

**Primary behavioural sub-decisions:**

- **Census scope = alive `fulcrum` (all commands) + `fake_worker_core`, `fake_mcp_stdio_core`; unix `ps`-enumeration filtering the FULL image basename + `/proc/<pid>/environ` marker read; Windows `tasklist /FO CSV /FI "IMAGENAME eq <image>.exe"` (the issue's own primitive, with `/FO CSV` so rows parse uniformly).** No `-f` / fuzzy full-command-line matching anywhere.
- **`fake_mcp_stdio_core` is in the match set but is the census's epsilon, not its primary target:** it is spawned only by the ENGINE's fixture/MCP tests, not by daemon tests, so a census that matches it catches an engine-suite leak (second-order) with an elevated false-positive surface on developer machines. Kept at primary-census severity; the difference is documented, not implemented as special-casing.
- **The pure classify function is the single source of truth**, shared by the live paths and the `--self-test` fixture harness — same house shape as the allocator guard's `run_check` over `--input` dumps. The census does real enumeration live (`ps`/`tasklist`) and real tests via fixtures AND one live planted process (see "Why `--input`" and `--self-test` below).

**macOS run-scoping is UNVERIFIED from this machine, and the census REFUSES rather than certifies on an unreadable arm.** This box is Linux (kernel 6.x, procps-ng 4.0.6); no macOS behaviour was asserted. What the plan ships, honestly: on macOS the census attempts `ps eww -o pid=,args= -p <pid>` (BSD `ps` env-print form) to read a candidate's env. Two things are known from this machine and from the ecosystem: (a) the OLD plan's spelling `ps eww -o pid= -p <pid>` is broken on every platform — measured here: with only a `pid=` column the output is just the number, no env, no args, nothing to classify — so the flag spelling is fixed to `-o pid=,args=` (the env suffix is only visible when an args/comm column is requested; measured: `ps eww -o pid=,args= -p <pid>` prints `… args … FULCRUM_CI_RUN_MARKER=…`); and (b) macOS restricts reading another process's env/argv (SIP / `proc_security.ptrace_deny_attach`), and unlike Linux's `/proc/<pid>/environ` (readable by any same-user process when `ptrace_scope=0` — measured above, this box is `0`) there is no documented same-user read of another process's env on macOS. **Therefore the census's macOS rule is: if a candidate's marker CANNOT be read, the census REFUSES — exit 2, with a message that the run-scope could not be verified on this platform — it NEVER certifies clean on the strength of "could not look".** The macOS branch reports the same limitation in its own output and in the script header ("macOS run-scoping is unverified here; a macOS leg that cannot read a candidate's env exits 2 rather than passing on a look it could not take"). The `--self-test`'s macOS fixture cases run on the shared parser (env-lookup seam), and the live macOS prove-it step's expectations are gated `#[cfg]-style` by the branch itself: *under macOS CI, a live census that cannot read a candidate's env must exit 2 (red), and THAT is the honest pass condition for the step.* The step pair is specified so that a macOS leg whose unix env-read works passes normally and one that cannot read exits 2 **red** — the named failure class is a leg that passes because it could not look, which the exit-2-on-unreadable rule makes impossible. A macOS-specific vet of the `ps eww` flag set is called out as `UNVERIFIED:` below (the fallback reserved is `ps e -o pid=,args=`), and the `cargo check --target x86_64-pc-windows-gnu` bar is unchanged (this task runs no cargo command).

**Windows can't be proven here either:** `tasklist`'s `/FI` + `/FO CSV` escape through MSYS bash's path mangling needs a live `windows-latest` run. The script's Windows half is fixture-proven (a real captured `tasklist` shape) on every platform and run-proven only on the Windows CI leg — the same honesty the repo already uses for `#[cfg(windows)]` arms (proctable/mod.rs:44-70, grounding §3).

**Exit-code contract (mirrors the allocator guard, documented for this script):** exit 0 = clean (or scoped-out processes found and left alone, with the count reported); exit 1 = leak(s) found (red); exit 2 = the census could not answer honestly — unreadable process table, unexported marker, a needed tool (`ps`/`tasklist`) missing, or a candidate whose env could not be read (macOS) — and refuses to certify anything; anything else is the tool's own failure. Apply `set -euo pipefail`, with `set +e` around the `ps`/`tasklist` invocations whose non-zero is a signal (no rows found), not an error.

**Vacuity floors (inherit the allocator guard's):**

1. **Unix:** the census must prove it READ the table before it can certify clean. `ps` exit 1 (no match) is fine; `ps` itself missing or failing on something other than "no match" → exit 2. If the enumeration yields zero candidates AND `/proc` cannot be read for the census's own pid (Linux), refuse (exit 2) — "no candidates at all while I cannot see the table" is not evidence.
2. **Windows:** if `tasklist` prints nothing it can classify (no rows, and no `INFO:`-report line), refuse with exit 2 — "an empty tasklist output is not evidence". A line that is neither a row nor an `INFO:` report → exit 2.
3. **Unexported marker (outside CI) = exit 2** — no marker recorded is not "clean"; the census answers only "are there processes from THIS run left", and without the discriminator it cannot read the question, so it refuses (the run-scoping rationale above). **The exit-2-with-a-message is deliberate, not a mystery red: a developer running the script locally gets a clear `error:` line ("no FULCRUM_CI_RUN_MARKER — the census only answers 'are there processes from THIS run left'; export one to run it in CI mode, or run --self-test to prove it can fail") and exit 2, and the plan records that this is the intended non-CI shape.** The `--self-test` proves this case exits 2 and never 0.

**`--input FILE` for self-test only** — the fixture harness feeds captured/synthetic candidate streams into `parse_candidate_stream` via `--input`, mirroring the allocator guard's `--input` exactly. **The live census REJECTS `--input`** (`--input` outside `--self-test` → `error: --input is for the self-test harness only` + usage + exit 1): the live path must always read the real process table, so an `--input` mock can never sit between the census and the table — that is the vacuity floor's live half.
